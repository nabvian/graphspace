Computational graphs that say how they know what they claim

Graphspace builds typed tensor graphs with resource contracts. Shapes are checked while the graph is built, memory is planned and checked against the contract before anything runs, and every execution returns a record in which each claim names its basis: declared, proven, estimated, measured.

Run it in your browser View source 
pip install git+https://github.com/nabvian/graphspace
examples/demo.py
from graphspace import Graph, ResourceContract, TensorSpec

graph = Graph("classifier",
              ResourceContract.max_memory(65536, deterministic=True))
spec = TensorSpec((2, 4), dtype="float32", role="activation")
graph.input("left", spec)
graph.input("right", spec)
graph.output(graph.relu(graph.add("left", "right")))

result, record = graph.execute({"left": [1.0] * 8,
                                "right": [-2.0] * 8})
record.claim("peak_memory_bytes")   # Claim(..., basis=ESTIMATED)

What it does

Five guarantees, each checkable

Typed tensor specs

Shape, dtype, layout and role. Dimensions can be symbolic ("N"); a symbolic dimension broadcasts only against itself or 1, and reshape must preserve the element count provably.

Errors at construction

A shape or dtype mismatch raises while the graph is being built, before any data exists, naming the node, the expected and actual values, and a remediation.

Resource contracts

Declare a memory limit and determinism. The memory plan is checked against the limit at validation; a limit that cannot be verified because a dimension is unbound is refused, not assumed.

Memory planning

Liveness, buffer reuse and peak memory from declared dtypes, including a per-call bookkeeping allowance calibrated for each CPython version from 3.10 to 3.14.

Execution evidence

Every run returns an ExecutionRecord: graph digest, optional input/output digests, and claims whose basis says how each is known.

    Limitations, as documented

    What it does not do

    • The python backend computes float dtypes in Python float precision; the numpy backend computes in the declared dtype.
    • Float overflow, division by zero and invalid operations follow IEEE rules without warnings.
    • Peak memory is an estimate. It does not cover the one-time cost of loading a backend, inputs converted from another dtype, or the widened temporaries used to check integer overflow. The allowance is calibrated for CPython, so figures shown in this WebAssembly playground are CPython estimates, not measurements of the browser.
    • ExecutionRecord.deterministic is the declared contract. The PyTorch adapter validates shape and dtype only. Graphs have no conditional routing.

    Future upgrades · taken from the release checklist and documented limitations

    What comes next

    Graphspace 0.1 is a working prototype: every item ticked in the release checklist is implemented and tested. These are the open items, each one taken from that checklist or from a documented limitation.

    EvidenceBenchmarks on a second machine

    All four benchmark rounds ran on one machine. Repeating them on other hardware will show whether the time and memory results carry over.

    EvidenceTrained models and real data

    The round 4 model blocks run on random inputs with scaled weights. The next step is benchmarking trained models on real data.

    FeatureConditional routing

    Graphs have no branches today. Planned: control flow whose shapes, memory and contracts are still checked before execution.

    FeatureDeeper PyTorch integration

    The PyTorch adapter checks shape and dtype only. Planned: carry resource contracts and execution records across to PyTorch models.

    FeatureWider memory estimate

    Extend the peak-memory estimate to cover one-time backend loading, inputs converted from another dtype, and the temporaries used for integer-overflow checks.

    Toward 1.0Stabilise the experimental APIs

    Promote the NumPy backend, the claim and basis vocabulary, and the failure value formats from experimental to stable, as set out in API stability.

    TrustSigned release artifacts

    The release tag and commits are already signed. Next: PyPI trusted publishing with attestations, so every wheel can be traced to its build.

    TrustIndependent security audit

    A static scan and a manual review are done. The next step is an outside audit, followed by community testing and maintenance.
